# Lab05 API системийн тест

**Оюутан:** О.Шинэбаяр  
**Код:** B232270023  
**Хэрэгсэл:** Node.js `v24.14.1`; Newman-ийн хувилбар ба ажиллуулалтын тоон дүнг `results/` файлуудаар баталгаажуулна.

## API болон тестийн зорилго

Энэ лабораторийн ажил нь локал хичээлд бүртгүүлэх API-ийн `POST /registrations` үйлдлийг эквивалент анги, төлөөлөх утга, спецификаци, бодит кейс гэсэн дарааллаар шалгана. Тест бүр өөрийн шаардлагатай оюутан, хичээлийн өгөгдлийг PUT-ээр үүсгэдэг учраас collection-ийг дараалан болон давтан ажиллуулах боломжтой. Суурь collection нь бүртгэлийн дугаарыг яг нэг утгатай тэнцүүлж шалгахгүй.

## Сонголт ба төлөөлөх утгууд

| Сонголт | Эквивалент анги / төлөөлөх утга |
|---|---|
| studentID-ийн төлөв | Бүртгэлтэй идэвхтэй (`B232270023_01`); бүртгэлтэй идэвхгүй (`B232270023_03`); тухайн кейсд үүсгээгүй ID (`B232270023_02`) |
| Оюутны үзсэн хичээл | `CS201` үзсэн (урьдач хангана); хоосон `[]` (хангахгүй); олон урьдачийн нэгийг үзсэн (заримыг хангана) |
| courseID-ийн төлөв | `CS313` бүртгэлтэй; `CS313` бүртгэлгүй |
| Хичээлийн урьдач | Бүгд үзсэн (`['CS201']`); огт үзээгүй (`['CS201']` + `[]`); заримыг үзсэн (`['CS201','CS202']` + `['CS201']`); урьдачгүй (`[]`) |

Оюутны ID нь серверийн талаас урьдчилан үүсгэсэн утгуудыг л lookup хийдэг бөгөөд ID-ийн форматыг `POST` endpoint тусад нь баталгаажуулдаггүй. Иймээс “ID хүчинтэй” гэдгийг энд бүртгэлтэй эсэхээр төлөөлүүлэв.

## Collection ба oracle

`lab05-collection.json` нь дээрх 10 бие даасан кейсийг агуулна. Кейс бүр өөрийн PUT setup хүсэлтүүдийн дараа POST хийж HTTP статус болон `result` утгыг шалгана. Амжилтын кейс мөн `registrationID` тоон төрөлтэйг баталгаажуулах боловч хуримтлагдах яг утгыг хүлээлт болгохгүй. Урьдачийн алдааны кейсүүд `missing` массивыг давхар шалгана. Сүүлчийн нийтийн API кейс JSONPlaceholder-ийн эхний хэрэглэгчийн нэрийг шалгаж нийт гурван oracle хэрэглэнэ.

| Collection | POST тохиолдол | Нийт assertion |
|---|---:|---:|
| Локал API | 10 | 24 |
| JSONPlaceholder | 1 | 3 |
| Нийт | 11 | 27 |

Тоо нь `newman-pass.txt`-ийн `assertions` executed мөртэй ижил байх ёстой.

## Newman-ийн ажиллуулалт

| Ажиллуулалт | Exit code | Хүлээлт |
|---|---:|---|
| PASS: `lab05-collection.json` | `0` | Assertions failed `0` |
| FAIL: `lab05-collection-fail.json` | `1` | Зориуд буруу статусын oracle-оос assertions failed `≥ 1` |
| DOWN: сервер унтраалттай | `1` | Гаралтад `ECONNREFUSED` байна |

PASS гүйлт 27 assertion, 0 failed, exit code 0; FAIL гүйлт 27 assertion, 1 failed, exit code 1; DOWN гүйлт 27 assertion, 24 failed, exit code 1 гарсан. DOWN үед 24 локал API шалгалт сервер унтарсан учраас унаж, JSONPlaceholder-ийн 3 oracle амжилттай болсон. Бүрэн Newman гаралт `results/newman-pass.txt`, `results/newman-fail.txt`, `results/newman-down.txt` дотор байна. DOWN үеийн `ECONNREFUSED` нь TCP холболт тогтоогүй интерфейсийн алдаа; FAIL үеийн assertion уналт нь серверийн хариу ирсний дараа oracle хүлээлт зөрсөн алдаа юм.

## Үр дүнгийн хэлэлцүүлэг

1. Эквивалент ангийг тодорхойлохдоо бүртгэлтэй эсэх ба идэвхтэй эсэхийг тусдаа сонголт болгох шаардлагатай байв.
2. Хичээлийн урьдачийг хангах эсэх нь оюутны үзсэн хичээлтэй хамт авч үзэх хамааралтай сонголт юм.
3. API-д оюутны ID буруу форматтай эсэхийг тусад нь шалгах дүрэм байхгүй учраас формат бус, бүртгэлийн төлөвөөр төлөөлүүлсэн.
4. Үзсэн хичээлийн жагсаалт хоосон байх нь хүчинтэй төлөв тул дангаараа алдаа биш.
5. Урьдач нөхцөлгүй хичээлд бүртгүүлэх нь хоосон жагсаалт ба `every`/`filter`-ийн зан төлөвийг шалгах хязгаарын тохиолдол байв.
6. Оюутан байхгүй болон хичээл байхгүй гэсэн хоёр алдааг зэрэг үүсгэх боломжтой бөгөөд API `ERROR_NO_STUDENT`-ийг түрүүлж буцаадаг.
7. Идэвхгүй оюутан болон байхгүй хичээлийг хослуулахад API идэвхгүй төлөвийг түрүүлж шалгадаг.
8. Хоёр алдааны хослолын шалгалтууд API-ийн шалгалтын дарааллыг ил тод болгосон.
9. Анхны гүйлтэд давтагдсан ID-с шалтгаалсан тестийн хамаарал илэрсэн; кейс тус бүрд ялгаатай ID өгсний дараа бүх 27 PASS assertion амжилттай болж, API-ийн согог илрээгүй.

## Нийтийн API-ийн харьцуулалт

JSONPlaceholder нь зөвхөн GET хүсэлтээр бэлэн өгөгдөл уншуулдаг тул өөрийн in-memory API шиг кейс бүрийн өмнө төлөв үүсгэх шаардлагагүй байсан; харин интернет болон гадаад үйлчилгээний хүртээмжээс хамаарна.

## Ажиллуулах

```powershell
node server.js
```

Өөр PowerShell цонхонд:

```powershell
New-Item -ItemType Directory -Force results | Out-Null
newman run lab05-collection.json 2>&1 | Tee-Object -FilePath results/newman-pass.txt
$passExit = $LASTEXITCODE
newman run lab05-collection-fail.json 2>&1 | Tee-Object -FilePath results/newman-fail.txt
$failExit = $LASTEXITCODE
```

DOWN шалгалтын өмнө серверийг `Ctrl+C`-ээр зогсоогоод:

```powershell
newman run lab05-collection.json 2>&1 | Tee-Object -FilePath results/newman-down.txt
$downExit = $LASTEXITCODE
```

PowerShell дээр pipeline-ийн дараа `$LASTEXITCODE`-ийг шууд хадгалж шалгана.
